# Workflow Runner technical decisions

This document records owner-approved technical choices. Workflow Editor's Decision Atlas owns product intent; Workflow Runner owns one-run execution, never authoring or orchestration.

## TECH-004 — Bounded per-consumer stream queues and slowest-consumer backpressure

- **Status:** approved 2026-10-16; owner selected option A. Implementation tracked by [#12](https://github.com/moritzbrantner/workflow-runner/issues/12).
- **Decision:** For an output with multiple active streamed consumers, the runner delivers each chunk in order to each consumer via an independently bounded per-consumer queue. Production cannot advance past the configured capacity of **any active consumer**: the slowest active consumer imposes backpressure on the upstream producer. Do not silently drop, reorder, replay or eagerly buffer an unbounded stream; do not require a user-authored Tee node or rerun the producer per consumer.
- **Lifecycle:** Register active consumers before producer delivery; handle completion, consumer cancellation, failure and upstream cancellation by releasing queue capacity and waking blocked producer/consumer operations. No blocked operations may leak after a run ends. Bound queue capacity by explicit resource limits and preserve cancellation responsiveness. Any decisions about concrete numeric queue sizes, failure policy and resource budgets require representative tests rather than invented product defaults.
- **Authority:** Workflow Editor owns static TypeScript payload compatibility and orthogonal buffered/streamed port metadata (TECH-003). Runner owns actual chunk fan-out, queue lifecycle, ordering and backpressure. Workflow Engine owns durable run state and dispatch and may persist only JSON-safe references/metadata, not raw binary chunks or live streams. Preserve existing compiled-v1 JSON-only runs.
- **Acceptance:** Use the actual compiled contract to run one producer and two differently paced consumers; verify exact ordered byte delivery to both, single producer execution, bounded queue occupancy and producer suspension, early cancellation/error cleanup, and producer/consumer overlap without stage deadlock. Verify buffered behavior and compiled-v1 compatibility. This decision does not claim the feature has shipped.

## TECH-005 — Executor-declared retries with no-retry default

- **Status:** owner-approved 2026-10-16, choice A. Implementation tracked in [#8](https://github.com/moritzbrantner/workflow-runner/issues/8).
- **Decision:** The host-registered executor/adapter declares its retry policy: which errors are transient and retryable, a finite maximum attempt count, optional timeout and bounded backoff, and the idempotency guarantee or key that makes another attempt safe. The default is **exactly one attempt, without automatic retry**. A global retry setting, generic runtime transient-error guessing, or another executor's policy must never implicitly repeat an operation.
- **Execution safety:** Retry only when the executor's policy explicitly classifies the observed failure as retryable and repeated execution is safe. Cancellation prevents further attempts and aborts the active attempt. Timeouts request cancellation through the existing AbortSignal, with distinct stable outcome classifications for timeout, cancellation, permanent failure and retry exhaustion. Expose attempt number and reason for provenance; use deterministic injected clock/sleep seams for tests rather than nondeterministic sleeps.
- **Ownership:** Runner enforces declared per-executor mechanics and lifecycle; adapters own their side effects and resource cleanup. Workflow Engine owns durable dispatch, queues and persistence, not duplicate in-run retry classification. No provider-specific client or global retry orchestrator is introduced.
- **Acceptance:** Issue #8 verifies one-attempt default, explicit retryable and permanent failures, no retry of non-idempotent side effects, cancellation and timeout races, exhausted attempts and deterministic lifecycle evidence. This decision does not claim implementation.

## TECH-006 — Local iteration/depth bounds plus run-wide execution budget

- **Status:** owner-approved 2026-10-16, option A. Implementation tracked in [#13](https://github.com/moritzbrantner/workflow-runner/issues/13).
- **Decision:** Every structured iteration Node enforces its own explicit finite iteration limit, and every recursively referenced workflow enforces its declared finite invocation-depth limit. In addition, the runner enforces an independent **run-wide execution budget** shared by nested iterations and recursive invocations so a product of individually finite limits cannot cause uncontrolled aggregate work. All are enforced before dispatch and as execution proceeds. Exhausting one bound must never launch one extra iteration or invocation.
- **Accounting and results:** Charge the global budget against a deterministic, documented unit of execution work (including nested activity); retries under TECH-005 cannot evade accounting. Surface the exhausted local or global limit, actual counts, and provenance in structured diagnostics. Convergence and exhausted-limit results follow the existing product rule: if there is a tracked valid best candidate, return it explicitly as partial/non-converged; otherwise report no valid result. Cancellation, timeouts and executor errors remain distinct. Do not invent default numeric budgets or a domain-specific quality metric.
- **Boundaries:** Consume an explicitly versioned compiled contract from Workflow Editor TECH-002 / #19. Workflow Runner owns budget accounting, cancellation and execution; Workflow Editor owns authoring/type checks, Workflow Engine owns dispatch and durable state. Preserve compiled-v1 ordinary DAG behavior.
- **Acceptance:** #13 must independently test nested loops, recursive references, run-wide exhaustion despite locally valid bounds, no post-limit dispatch, retry accounting, early convergence, partial best-candidate provenance, no-candidate failure and compatibility with existing executions. This record is not implementation evidence.

## TECH-007 — Run-wide budget counts actual node execution attempts

- **Status:** owner-approved 2026-10-16, option A. Refines TECH-006; implementation belongs to [#13](https://github.com/moritzbrantner/workflow-runner/issues/13).
- **Decision:** The run-wide work budget counts **actual node execution attempts**, including each retry and attempts inside nested iterations and recursively referenced workflows. Consume one unit atomically **before starting** each actual attempt (including built-in node executors); never dispatch an attempt after the budget has been exhausted. Structural iteration/reference traversal alone does not consume an extra attempt unless it actually dispatches an executor. Skipped/inactive nodes and never-started attempts do not count.
- **Semantics:** Keep finite local iteration and recursive-depth limits from TECH-006 independently enforced. Charge retries according to TECH-005 with no exception for transient failures; cancellation and timeouts cannot trigger hidden unbudgeted attempts. Count attempts deterministically, record attempted node/invocation and current usage in run evidence, and identify run-wide exhaustion distinctly from local limits. Preserve existing converged/partial/non-converged/no-valid-candidate/error classifications.
- **Boundary and acceptance:** Runner owns the counter and pre-dispatch gate; Workflow Editor supplies a versioned compiled bound contract; Workflow Engine owns orchestration, not per-attempt accounting. No weighted-cost model or invented default numerical budget is approved. In #13 test nested and retried attempts, boundary equality, inactive/skipped nodes, cancellation races, and no off-by-one dispatch, retaining compiled-v1 DAG compatibility. Recording this decision does not claim implementation.

## TECH-008 — Terminable isolation for non-cooperative executors

- **Status:** owner-approved 2026-10-16, option A. Refines TECH-005; implementation tracked in [#8](https://github.com/moritzbrantner/workflow-runner/issues/8).
- **Decision:** Ordinary host-registered executors may use cooperative cancellation through AbortSignal when they can reliably stop and release resources. An executor that cannot guarantee cooperative cancellation **must run through a host-owned, terminable isolation boundary** (for example, a managed subprocess with a bounded shutdown/kill path). Do not mandate process isolation for every cooperative executor, and do not merely stop awaiting a non-cooperative operation while leaving it indefinitely active.
- **Lifecycle:** Timeout or cancellation first signals the active attempt to stop; if it does not terminate within its bounded shutdown contract, the isolation adapter forcibly terminates its work and completes cleanup. Prevent detached runner-owned tasks and new retries after cancellation. Distinguish a timed-out/terminated attempt, ordinary cancellation, cleanup failure, and permanent/retry-exhausted errors in structured evidence. Termination of a local process cannot guarantee rollback of remote external side effects: retry still requires TECH-005's explicit idempotency policy.
- **Authority:** Runner coordinates one-run cancellation and safe attempt lifecycle; host adapters own actual process/network/resource isolation and cleanup. Workflow Engine owns durable orchestration, not a duplicate execution sandbox. Preserve existing compiled-v1 workflows and ComfyUI's own inference/queue authority.
- **Acceptance:** #8 covers a cooperative executor and a deliberately uncooperative isolated executor; verifies abort, bounded escalation, termination, resource cleanup, no detached runner work, cancellation/retry races and truthful side-effect limits. The decision does not claim implementation.

## TECH-009 — Workflow-declared candidate evaluator and comparator

- **Status:** owner-approved 2026-10-16, option A. Refines TECH-006/007; implementation tracked in [#13](https://github.com/moritzbrantner/workflow-runner/issues/13).
- **Decision:** A structured iterative workflow explicitly declares how candidate outputs are validated and compared. The runner evaluates that declared contract on each completed iteration, retains the best **valid** candidate and its evidence, and does not invent a domain-specific quality metric or treat the last candidate as inherently best. The declaration and its referenced evaluator/comparator must be resolved and validated as part of the versioned compiled workflow contract, without allowing arbitrary untrusted executable code in metadata.
- **Determinism and failure:** Candidate comparison uses declared deterministic ordering and tie behavior; absent/invalid candidates cannot displace a valid candidate. Report evaluator failures distinctly rather than claiming convergence or silently choosing a result. Early convergence uses the separately authored stop condition. On local or run-wide limit exhaustion, return the tracked valid best candidate as explicitly partial/non-converged with stop reason, iteration count and available evaluation provenance; without one, report no valid result. Cancellation, timeout and executor failures remain distinct. Evaluation that invokes an actual Node executor consumes run-wide attempt budget under TECH-007.
- **Ownership and evidence:** Workflow Editor owns typed authoring/validation and versioned compilation (TECH-002 / #19 / #64). Workflow Runner executes declared evaluation/comparison and tracks best candidates; domain logic stays in host-registered executors. No second editor, optimizer, or global orchestration engine. #13 must test non-monotonic candidate quality, deterministic ties, invalid/absent candidates, evaluator failure, convergence, budget exhaustion and compiled-v1 compatibility. This decision is not implementation evidence.

## TECH-010 — Independent stream-consumer cancellation and failure

- **Status:** owner-approved 2026-10-16, choice A. Implementation tracked in [#12](https://github.com/moritzbrantner/workflow-runner/issues/12).
- **Decision:** A cancelled or failed downstream stream consumer stops receiving chunks, releases its bounded queue, and no longer applies backpressure. Other active consumers continue receiving their chunks. When no active consumers remain, stop upstream production and clean up its resources. Preserve TECH-004's bounded queues and lossless delivery for each remaining active consumer.
- **Scope:** This is the straightforward default fan-out behavior, not a new configurable failure-policy framework. Preserve ordinary run-level error reporting and cancellation authority; do not silently label a failed workflow run successful merely because one branch continued. Verify consumer removal and upstream stop in focused regression tests without expanding this issue into an exhaustive network-exception matrix.
- **Steering boundary:** The owner explicitly requested that future technical questions emphasize basic, user-visible workflow functionality rather than repetitive low-level network, exception, and special-case decisions. Implementation agents should apply existing conventions and settled error policies to routine cases instead of escalating each one.

## TECH-011 — Persist node results at run completion by default, with per-node opt-in

- **Status:** owner-approved 2026-10-17; choice **B with explicit per-Node persistence override** for [Runner #23](https://github.com/moritzbrantner/workflow-runner/issues/23).
- **Product basis:** Workflow Editor Decision Atlas 5.8 (run history/per-Node inspection) and 5.13 (selectively rerun from a chosen Node using compatible previous results).
- **Decision:** For ordinary Nodes, Runner collects completion evidence and outputs during execution and supplies them at the **terminal run result** for Engine/host persistence, including failed runs with completed upstream Nodes. Do not continuously write every Node by default. A Workflow Document can explicitly enable **persist on completion** for an individual Node; Editor authors the setting and preserves it through the versioned compiled Node contract. Runner emits a completed, provenance-bearing Node result to the existing host/Engine persistence boundary as soon as that opted-in Node finishes. No global always-on per-Node write policy or runner-owned database.
- **Durability and replay:** Engine/host owns durable storage and confirms a successful write; an emitted event or an in-memory output is not automatically a durable checkpoint. Include pinned workflow version/digest, run/Node/attempt identity and input/result provenance so a later selective rerun can reuse only verified compatible results. A crash can lose ordinary, not-yet-terminal results; opted-in Nodes survive only once their persistence is acknowledged. Never replay completed external effects merely to reconstruct missing evidence; an unrecorded effect does not establish safe retry. Respect TECH-005's executor idempotency policy.
- **Boundaries and compatibility:** Reuse current Runner lifecycle/results and Engine's `WorkflowRunDispatcher` / `WorkflowEngineStore` seams; don't add a second history store or execution system. Keep persisted values JSON-safe, using verified references for binary artifacts rather than raw bytes, streams or secrets. [Engine TECH-001](https://github.com/moritzbrantner/workflow-engine/blob/main/docs/technical-decisions.md) still requires **immediate** durable checkpoints at human-input/approval waits regardless of individual Node settings. Existing compiled-v1 documents without the optional metadata retain their behavior.
- **Acceptance:** Runner #23 and the owning Editor/Engine contracts prove: successful and failed terminal-run results persist upstream evidence by default; opt-in writes survive a pre-terminal crash after acknowledgment; ordinary non-opted-in results are not falsely reported durable; selective reruns reuse compatible pinned results and reject changed inputs/versions; no duplicate external side effects; typed settings roundtrip and legacy compiled workflows remain valid. This is a decision, not implementation evidence.
